Evolución Histórica de las Bases de Datos

1960s

Sistemas de Archivos

Primeros sistemas basados en archivos planos con limitaciones de integridad y redundancia.

1970s

Modelo Relacional

Edgar F. Codd propone el modelo relacional, revolucionando el manejo de datos estructurados.

1980s

SQL y SGBD Comerciales

Aparecen Oracle, DB2 y SQL se establece como estándar para consultas.

1990s

Bases de Datos Objeto-Relacionales

Integración de características orientadas a objetos en sistemas relacionales.

2000s

Revolución NoSQL

Apache Cassandra, MongoDB y Redis emergen para manejar datos no estructurados.

2010s

Era de la Nube

Amazon RDS, Google Cloud SQL y Azure SQL Database dominan el mercado.

2020s

Bases de Datos Multi-Modelo

Sistemas que soportan múltiples modelos de datos simultáneamente.

Fundamentos de Bases de Datos - Teoría Completa

Arquitectura fundamental de un sistema de base de datos moderno

Definición Académica

Una base de datos es una colección organizada de datos interrelacionados, almacenados en un sistema informático, diseñada para permitir el almacenamiento, recuperación, modificación y eliminación eficiente de información mediante un Sistema Gestor de Bases de Datos (SGBD).

Componentes Arquitectónicos Principales

Diagrama de componentes de un Sistema Gestor de Bases de Datos

Motor de Almacenamiento

Gestiona el almacenamiento físico de datos en disco, incluyendo gestión de archivos, caché y recuperación.

Procesador de Consultas

Interpreta y optimiza consultas SQL, generando planes de ejecución eficientes.

Gestor de Transacciones

Asegura las propiedades ACID y maneja la concurrencia entre múltiples usuarios.

Escalado Vertical (Scale-Up)

Aumentar la capacidad del servidor existente: más CPU, RAM, almacenamiento más rápido.

Ventajas
  • Implementación simple
  • Sin cambios en la aplicación
  • Consistencia garantizada
  • Menor complejidad operacional
Limitaciones
  • Límites físicos de hardware
  • Punto único de fallo
  • Costos exponenciales
  • Downtime durante upgrades

Infraestructura de servidor para escalado vertical

Escalado Horizontal (Scale-Out)

Agregar más servidores y distribuir la carga entre ellos.

Ventajas
  • Escalabilidad casi ilimitada
  • Alta disponibilidad
  • Costos lineales
  • Tolerancia a fallos
Desafíos
  • Complejidad de implementación
  • Consistencia eventual
  • Mayor latencia de red
  • Gestión distribuida compleja

Sharding (Particionamiento Horizontal)

Distribuir datos entre múltiples bases de datos basándose en una clave de shard.

Estrategias de Sharding
  • Por Rango: Basado en rangos de valores
  • Por Hash: Distribución uniforme
  • Por Directorio: Tabla de lookup centralizada
  • Geo-Sharding: Por ubicación geográfica
Consideraciones
  • Elección de clave de shard
  • Re-balanceo de datos
  • Queries cross-shard
  • Backup y recovery

Réplicas de Lectura

Múltiples copias de solo lectura para distribuir la carga de consultas.

Arquitectura
  • Un maestro para escrituras
  • Múltiples réplicas para lecturas
  • Replicación asíncrona/síncrona
  • Balanceo de carga automático
Ventajas
  • Mejor performance de lecturas
  • Alta disponibilidad
  • Recuperación ante desastres
  • Escalabilidad lineal

Sistema para detectar transacciones fraudulentas usando modelos de machine learning integrados.

Arquitectura

  • Modelos scikit-learn empaquetados

  • Dashboard de monitoreo en tiempo real
Resultados
  • 95% de precisión en detección
  • Latencia < 100ms por transacción
  • Reducción de 80% en fraudes
  • Escalabilidad a 10,000 TPS
-- Función para scoring de fraudes
CREATE OR REPLACE FUNCTION score_fraude(
  monto NUMERIC,
  hora_transaccion INT,
  ubicacion VARCHAR
) RETURNS NUMERIC AS $$
  import pickle
  modelo = pickle.loads(pg_model_data)
  features = [monto, hora_transaccion, hash(ubicacion)]
  return modelo.predict_proba([features])[0][1]
$$ LANGUAGE plpython3u;
